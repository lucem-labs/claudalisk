# CLA-0089: The host drives Roslyn's server for C# and TypeScript 7's server for TypeScript, and applies their edits by fixed rules

- **Status:** accepted
- **Date:** 2026-11-15
- **Area:** workflow
- **Enforced by:** reviewer (CLA-0023); the spike's tests of the edit-applier rules and the capability probe. No host is built (CLA-0092).
- **Issue:** #203, #200, #208

## Context

CLA-0088 plans a live language-server host per worktree (X1) that drives the servers directly, because Claude Code's `LSP` tool has no rename, code action or file-rename. The choice of csharp-ls as the C# server was never recorded. It came in with CLA-0080, inherited from the official `csharp-lsp` plugin, and Roslyn's own server was never compared with it.

The spike drives csharp-ls 0.28.0, `roslyn-language-server` 5.13.0-1.26514.10 and `tsc --lsp --stdio` 7.0.2 over stdio from a Node client with no dependency. The two dotnet tools are pinned in a tool manifest and TypeScript in the spike's `package.json`. The fixture is the app from `tools/new-app.mjs` plus small C# and TypeScript cases: overloads, an interface with two implementations, a partial class, a record property, a regex and a JSON context that source generators fill in, a barrel `index.ts`, and a file rename. After every edit the spike builds and runs the tests, and a case passes only when they pass, the expected sites changed, and an applied code action changed some file content or made a resource operation. For C# that is `dotnet build` of the whole `backend/Proof.slnx`, then the test projects: the cases' own, and the app's `Proof.ArchitectureTests`, `Proof.Api.Tests` and `Proof.Modules.Ordering.Tests`. The last three create a PostgreSQL database in a container, so they run only where `docker info` answers `linux`: on ubuntu, and not on windows or macos, whose runners have no Linux containers. The results name the skipped projects, and on windows and macos the app's three test projects were not run. For TypeScript it is `tsc -b` and the unit tests. A build of the whole solution took 3.3 to 3.8 s on ubuntu, 2.6 to 4.0 s on windows and 3.8 to 12.2 s on macos, and the tests 0.3 to 0.9 s where only the cases' project runs and 16.7 to 17.2 s on ubuntu with the container tests. The numbers below come from the CI run on `f46dfd1`: https://github.com/lucem-labs/claudalisk/actions/runs/43754760422.

What the three OSes showed:

- **Correctness was the same on ubuntu, windows and macos.** There are 19 C# cases per server and 14 TypeScript cases, which include a second diagnostics case where the client does not advertise pull.

  - csharp-ls: 16 pass, 1 unsupported (rename file), 2 fail (move type, change signature).
  - TypeScript: 8 pass, 6 unsupported (diagnostics without pull, type hierarchy, extract, inline, move, change signature).
  - Requiring an applied code action to change something, and an applied server `workspace/applyEdit` to have been accepted, moved no result: every extract, inline, move and organize-imports pass of the earlier run still passes.

The polls run back to back, and the figure is the request start plus the duration of the first correct answer, so a server that answers slowly is not helped or penalised by a poll interval. ## Decision

- **The C# server is Roslyn's own, `roslyn-language-server`.**
  - It passes every case csharp-ls passes except the diagnostics case without pull, and two more. Its "Rename file to X.cs" and "Move type to X.cs" code actions return real RenameFile and CreateFile operations. csharp-ls offers the first with an empty edit, and sends the second as a text edit for a file that does not exist, with no CreateFile.
  - It renames only the overload under the cursor. csharp-ls renames every overload, which a model asking for one rename does not expect.
  - It returns references that lie in source-generated files, as `roslyn-source-generated://` URIs. csharp-ls returns none, so a rename or a reference count that depends on generated code is silent there.
  - Its cold start is probably lower, by a margin that varies from run to run. Its warm `findReferences` is about 0.5 s a call, which is acceptable for a tool call a model makes, and its memory is higher.
  - **The 0.5 s is a wait inside the server and the client cannot remove it.** The spike timed `textDocument/references` four ways on a loaded server, 25 calls each: plain, with a `partialResultToken`, with a `workDoneToken`, and with both. All four took the same time on every OS, 501 to 502 ms median on linux, 502 to 504 ms on windows and 556 to 582 ms on macos. With a `partialResultToken` the four locations came back through `$/progress` and the response was empty, and the wait did not change. The server sent `window/workDoneProgress/create` twice in the whole run, which held 100 references calls, so a call does not start a progress round trip. In Roslyn's references handler (read on the main branch at the time of this ADR, not at the pinned version), `FindUsagesLSPContext` reports results through an `AsyncBatchingWorkQueue` with `DelayTimeSpan.Medium`, which is 500 ms, and `OnCompletedAsync` waits for the current batch to finish. That is the delay, and it applies to a request that is not streaming. The host pays it once per `findReferences`, uses the plain call shape, and does not poll `findReferences` in a loop. `prepareRename` took under 2.1 ms on the same server.
  - It is published only as a prerelease, so the host pins an exact version in a tool manifest, and a generated app's CI gets the tool from the DinD runner image (CLA-0088). csharp-ls stays what CLA-0080's `LSP` plugin runs, since no host is built (CLA-0092).
  - The host must open the solution with the `solution/open` notification, wait for `workspace/projectInitializationComplete` and answer `workspace/configuration`, `client/registerCapability` and `window/workDoneProgress/create`. Some actions, such as "Add parameter", arrive as a command `roslyn.client.nestedCodeAction` that carries child actions. The host resolves a child with `codeAction/resolve` and applies its edit.
- **The TypeScript server is `tsc --lsp --stdio` from the `typescript` package, pinned exactly.** The generated app's own `tsc -b` ran on 6.0.3 and passed after edits made by the 7.0.2 server, so the two versions are independent.
  - Rename returns `changes`. By default it keeps a barrel's public name: renaming `formatPrice` gives `export { renderPrice as formatPrice }` and leaves importers alone. Answering `workspace/configuration` with `typescript.preferences.useAliasesForRenames: false` renames every site. The host asks for the second form and says so.
  - It sends diagnostics only when asked (`textDocument/diagnostic`). Source actions come back only when the request lists them in `only`. At the error sites of the cases it returned no quick fix.
  - It does not advertise type hierarchy, and offers no extract, inline or move.
- **Diagnostics: where the client advertises pull, no server pushes; where it does not, only csharp-ls does.** The spike broke the build with one edit and waited 20 s for `textDocument/publishDiagnostics`, twice per server. With the client advertising `textDocument.diagnostic`, none of the three pushed, and all three answered `textDocument/diagnostic` with the error. With the client not advertising it, csharp-ls pushed the error (2 diagnostics), and Roslyn and TypeScript still pushed nothing and are unsupported there, on all three OSes. So Roslyn and TypeScript can give diagnostics only by pull, and csharp-ls's push is switched off by a client that advertises pull. The host advertises pull and pulls diagnostics after each edit for D1 and on request for D2. It does not wait for a push.
- **The host applies a `WorkspaceEdit` by these rules.** The spike implements them with a test for each; a host built later must carry the same tests.
  - **Shapes:** `changes`, `documentChanges` with `TextDocumentEdit`, and the resource operations `CreateFile`, `RenameFile` and `DeleteFile` with `overwrite`, `ignoreIfExists`, `ignoreIfNotExists` and `recursive`. The client advertises `failureHandling: abort`.
  - **Positions are UTF-16 code units.** A character past the end of a line is clamped to the end. A line past the end of the document is refused.
  - **Edits in one document apply from the end to the start.** Inserts at one position keep the order they were sent in.
  - **Overlapping edits are refused.** Edits that only touch are allowed.
  - **Every URI must be a `file:` URI inside the workspace root.** Anything else is refused, including source-generated documents and a path that leaves the root.
  - **A `TextDocumentEdit` version must match the open document.** A version for a document that is not open is refused. A null version skips the check. Documents are identified by their normalized path, compared without regard to case on windows and macos, so `file:///c%3A/x` and `file:///C:/x` are one document, in this check, in the host's open-document versions and when matching pushed diagnostics.
  - **`CreateFile` onto an existing file and `RenameFile` onto an existing file are refused unless `overwrite` is set.** `ignoreIfExists` skips the operation. A missing source, a text edit for a missing file, and a folder rename are refused. `DeleteFile` of a missing file is refused unless `ignoreIfNotExists` is set, and of a folder unless `recursive` is set.
  - **Nothing is written when anything is refused.** The host checks every operation against an in-memory copy of the files, where a later operation sees an earlier one, and writes only after all of them pass.
  - **Line endings and a byte order mark are kept as found.** Inserted text takes the document's first line ending.
  - **After a write, the host sends `workspace/didChangeWatchedFiles`, and a full-text `textDocument/didChange` with the next version for each open document.** A refused edit that came as `workspace/applyEdit` is answered with `applied: false` and the reason, and the host records each such edit with whether it was applied and whether it changed anything. The host installs its `workspace/applyEdit` and `workspace/workspaceFolders` handlers before it sends `initialize`, so a server that edits during start-up is answered.
- **Build and test after every edit.** A host edit tool reports success only when `dotnet build` of the whole solution and the tests, or `tsc -b` and the unit tests, pass. A server answering is not evidence, and neither is a code action whose edit changes no file content and makes no resource operation, which the spike reports as unsupported. A test that cannot run on a machine, as the PostgreSQL tests cannot without a Linux container runtime, is reported by name as skipped and never silently.
- **The catalogue rows are amended by id:**
  - **N5, type hierarchy:** build for C# on both servers, which returned the right subtypes and supertypes of an interface and its implementations. TypeScript's server does not advertise it, so no N5 for TypeScript.
  - **E2, rename or move a file or type:** build for TypeScript through `workspace/willRenameFiles` followed by a RenameFile (imports in the barrel and the test were updated, `tsc -b` and the tests passed), and for C# on Roslyn through "Rename file to X.cs" and "Rename type to X". Not built on csharp-ls. The spike renamed files in place only, so moving a file to another folder or namespace is not shown.
  - **E3, change signature:** not available from code actions. At a call with an extra argument both C# servers offer "Add parameter", which changes one declaration and leaves other callers broken, and the build failed on all three OSes. TypeScript offers nothing. Claudalisk would build it as its own tool over references and edits, if the benchmark calls for it.
  - **E6, organize imports, fix all, quick fixes:** build the kinds each server returns. Applied and passing: TypeScript's `source.organizeImports` and `source.removeUnusedImports`, and "Remove unnecessary usings" on both C# servers. Roslyn also offers "Fix All" quick fixes, which the spike listed and did not apply. TypeScript advertises `source.fixAll` and returned none in the cases.
  - **E7, extract, inline, move:** build for C#. "Extract method" and "Inline temporary variable" were applied on both servers and passed. "Move type to file" passes on Roslyn only. TypeScript's server offers none.
  - **D1, diagnostics pushed after each edit, and D2, diagnostics on demand:** build both as one host feature over `textDocument/diagnostic`. D1 does not stay with the servers' own push, which only csharp-ls sends, and only to a client that does not advertise pull. Roslyn, the chosen C# server, and TypeScript push nothing in either mode, so the host pulls after each edit and hands the result to the model.
  - **X2, persistent index:** cold start calls for none. On this 12-project solution the first correct answer took 6 to 17 s for C# (medians per OS) and under 0.5 s for TypeScript, and later calls are fast. The host keeps the server running (X1). X2 is reconsidered only if the benchmark in #202 shows a larger solution waiting long on first use.

## Consequences

- No host is built (CLA-0092), so these choices and rules bind only a host that a later ADR builds.
- The host depends on a prerelease tool. A version bump is a change to the tool manifest and the DinD image together, and the spike's CI job on three OSes is the check that the new version still passes.
- The host carries server-specific duties: the Roslyn start sequence and nested actions, TypeScript's `only` filter and rename configuration. Each is covered by a case in the spike.
- A rename tool must report which overloads, and which generated or non-file locations, it did not change, because the two C# servers differ and generated sites cannot be edited.
- The generated app's frontend step that writes API types needs a container runtime, which the windows and macos runners lack. The spike asks whether a Linux container runtime answers and not which OS it runs on. Where none does, it logs the substitution and copies a committed schema, which must be regenerated when the template's backend endpoints change. The same answer decides whether the app's three PostgreSQL test projects run after a C# edit; on windows and macos they did not.
- The spike stays available to re-measure after a server upgrade, and its fixture is the same app that #202 builds its benchmark on.
